# Supabase migration rehearsal

These owner-only CLI tools copy data into a separate, initialized PostgreSQL database on the staging instance. They do not switch either app's database. Export files contain personal/workspace data: keep them outside Git in private directories, with mode 0600 files, and transfer only over SSH.

1. Run `node scripts/migration-rehearsal/export.mjs /absolute/new/private-directory` from the repository with the source `.env.local` available (or `SOURCE_ENV_FILE`). The Supabase service key stays in the exporting process. This performs only source reads. Two matching paginated snapshots detect changes during the export but do not provide a transactionally consistent snapshot. A production cutover requires a coordinated write freeze and fresh export.
2. Create a NEW database whose name starts `tasktracker_rehearsal_` on the existing local PostgreSQL port 55433. Initialize it using `scripts/postgres/migrate.mjs` with an owner connection. Do not change the shared runtime role password or staging environment.
3. Transfer `data.json` privately to the server. Run `import.mjs /private/path/data.json` as the database owner, with PGHOST, PGPORT=55433, and PGDATABASE set. The import rejects nonempty target tables, unknown source columns, inconsistent row shapes, and usable credentials. User triggers are disabled transactionally to avoid duplicate notifications/history; foreign keys and CHECK constraints stay enabled. Each imported column is compared using PostgreSQL's own types before committing.
4. Run `verify.mjs /private/path/data.json` with the same connection settings. It compares all imported fields and checks project/task/notification visibility under each profile's SQL identity. This is database authorization verification, not browser login verification or a comparison against live Supabase policies.
5. Make a private `pg_dump -Fc` backup and restore it into another NEW rehearsal database with `pg_restore --exit-on-error --single-transaction`. Run the same verifier against the restored copy. Preserve the cluster role definitions separately in the eventual full recovery plan; this rehearsal restores within the existing cluster.

The exporter downloads referenced `task-files` attachments and validates their sizes and SHA-256 hashes. Attachment directory installation and restore validation must be completed separately if the export contains attachments. It does not copy unreferenced bucket objects or other buckets. The 11 September rehearsal had zero referenced attachments, so this file-migration path was not exercised.

Supabase Admin API does not supply password hashes. Imported users retain IDs, emails and metadata but have null local password hashes and are disabled. Do not activate these accounts until a deliberate local-password setup has been completed. Supabase sessions are not migrated. No production cutover is performed by these scripts.

After explicit password authorization, `set-passwords.mjs` accepts a JSON object containing `password` on stdin and the private export path as its argument. It is restricted to the approved `tasktracker_rehearsal_20260911` database on port 55433, verifies the exact exported account set, salts each account independently, activates accounts, revokes sessions, and verifies every saved hash within one transaction. Do not put passwords in arguments, shell history, or checked-in files. The import/restore verifier's credential comparison intentionally no longer passes against an activated database; use it on the unchanged restore copy.

11 September 2026: actual export/import and backup/restore passed for 12 accounts, 3 projects, 10 memberships, 5 tasks, 3 comments, 8 notifications and 9 history entries. Other exported application tables were empty. Both copies passed 36 visibility assertions. Existing staging sample data remained intact and live HTTPS returned 200.
